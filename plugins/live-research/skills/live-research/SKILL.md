# Live Research

Use current evidence for material change-sensitive claims. Skip retrieval for
pure logic, mathematics, translation, mechanical transformations, and answers
fully established by supplied material. Research only the changing portion of a
mixed request.

## Establish the question

Identify the claims that could change the decision or implementation if wrong.
Record the relevant version, jurisdiction, environment, date range, or source
target. Inspect the actual project files, lockfiles, configuration, and tool
output first when the answer depends on a particular system.

## Retrieve and compare

1. Check which specialized documentation, account, or domain tools are callable
   in the current session. Installed or configured does not prove connected,
   healthy, entitled, or usable.
2. Prefer an already-callable primary-source route: official product MCP, vendor
   documentation, repository, regulator, standards body, filing, or original
   dataset. Use a library documentation service when it resolves the exact
   package and version. Use general web search to reach primary sources when a
   specialized route is unavailable.
3. For recent facts, search from the session date backward. For
   version-sensitive software claims, check official release notes, changelogs,
   tags, or announcements across the preceding six months; expand when that
   window cannot establish the behavior. Read the actual source page, not a
   snippet.
4. Compare sources to each other and to local project authority. Classify a
   disagreement as an outdated fact, compatibility conflict, intentional project
   constraint, or unresolved intent. Explain the practical impact before
   changing affected work.
5. For a technical stack, follow the material dependency chain: runtime, package
   versions, adapters, APIs, host support, and deprecations. Do not infer
   compatibility from one green component or from silence in release notes. For
   a statistic, verify issuer, method, population, period, and relevant
   limitations.

If an authoritative route fails, use the strongest safe alternative and state
the resulting limit. Do not promote a search snippet, secondary summary, memory,
or undated page into proof of current behavior. An undated page may be used when
identified as `undated; accessed YYYY-MM-DD`; corroborate it with dated evidence
when the conclusion is version-sensitive.

## Authority and sensitive information

Research may read permitted local material and make read-only source requests.
It does not authorize project edits, installs, messages, publication,
deployment, account changes, or disclosure of private data to an external
service. Keep credential values out of requests and output; use `${VAR}` names.
Carry forward authorization already granted for the actual task. When a missing
fact changes the conclusion, ask a focused question or mark the result
unverified; stop only the dependent action.

## Report

Lead with the answer and cite each material external claim near the claim with
the source's publication/update date, or an access date for an undated page.
Separate verified facts, interpretation, conflicting evidence, and unresolved
claims. Include exact versions and dates checked, material assumptions,
limitations, and the next action when a decision remains. Never invent a source,
quotation, test result, or approval.
